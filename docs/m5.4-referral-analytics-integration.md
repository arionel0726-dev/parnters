# M5.4 Referral Analytics Integration

Этот документ описывает выключенный по умолчанию контур аналитики Partners. Он не изменяет Legacy и не включает комиссии, выплаты или старый order ledger.

## Включение

В production оставить:

```env
REFERRAL_ANALYTICS_ENABLED=false
REFERRAL_TRACKING_ENABLED=false
CREATOR_FINANCE_ENABLED=false
PAYOUTS_ENABLED=false
LEGACY_RESOLVER_ENABLED=false
```

Для отдельного тестового окружения `REFERRAL_ANALYTICS_ENABLED` можно временно установить в `true`. Для Legacy → Partners нужен отдельный key ring `LEGACY_ANALYTICS_HMAC_KEYS`; ключи resolver и account linking для этого контура не используются.

## Redirect handoff

Переход по `GET /r/{code}` сначала проверяет активную ссылку, владельца-креатора, статус и срок действия. При включённой аналитике Partners создаёт attribution с окном 7 дней и добавляет к сохранённому разрешённому URL:

```text
https://vizaje-nica.com/ru/catalog/example?vp_attribution=<opaque-one-time-token>
```

В базе хранится только SHA-256 hash токена. Сам токен не содержит UUID партнёра и не логируется. При повторном запросе с тем же `vp-referral-visit` в течение 30 минут новая атрибуция и новый click не создаются. Новый валидный referral click для другого URL отзывает предыдущую атрибуцию этого visit key.

Legacy должен принять этот параметр на своём сервере, обменять его и сделать redirect на канонический URL без `vp_attribution`. Параметр нельзя сохранять в постоянной cookie или передавать дальше после обмена.

Partners передаёт visit key только между своим redirect route и API в заголовке `x-referral-visit-id`; cookie `vp-referral-visit` принадлежит только origin Partners.

## Handoff exchange

`POST /v1/internal/referral-analytics/attribution/exchange`

Тело:

```json
{"handoffToken":"<opaque-token>"}
```

Успешный ответ не раскрывает Partner UUID:

```json
{
  "attributionContext": "v1.<payload>.<signature>",
  "expiresAt": "2026-11-18T12:00:00.000Z"
}
```

Токен можно погасить только один раз. Повторное, просроченное или отозванное погашение возвращает `ATTRIBUTION_INVALID` и не выдаёт контекст.

## HMAC Legacy → Partners

Для аналитики используется отдельная переменная `LEGACY_ANALYTICS_HMAC_KEYS`. Формат — JSON-массив с одним активным ключом:

```json
[{"keyId":"legacy-analytics-to-partners-dev-2026-11","secret":"<base64url без padding, минимум 32 байта>","active":true}]
```

Заголовки:

```text
x-vp-key-id
x-vp-timestamp
x-vp-nonce
x-vp-signature
```

Canonical string:

```text
VP-HMAC-SHA256-V1
{keyId}
{HTTP method in upper case}
{pathname + query}
{timestamp}
{nonce}
{sha256(raw request body as UTF-8, lowercase hex)}
```

Строки соединяются одним `\n`, подпись — HMAC-SHA256 в lowercase hex. Timestamp допускает расхождение не более 60 секунд, nonce должен быть base64url-совместимым ровно 22 символа и повторно использоваться нельзя. Сервер хранит nonce в существующей database-backed таблице replay protection.

## Add to cart

`POST /v1/public/referral-analytics/events`

Маршрут доступен только при `REFERRAL_ANALYTICS_ENABLED=true`. Он не принимает Partner UUID и не считает присланные браузером цены подтверждённой выручкой.

```json
{
  "eventId":"2f3c0c2b-9cb9-4cf0-b8a2-c6d0f2c79f54",
  "eventName":"add_to_cart",
  "attributionContext":"v1.<payload>.<signature>",
  "occurredAt":"2026-11-11T12:00:00.000Z",
  "items":[
    {"legacyProductId":"11048","quantity":1}
  ]
}
```

Повтор того же `eventId` с тем же payload возвращает `200` и `idempotent: true`. Тот же ID с другим payload возвращает `409 IDEMPOTENCY_CONFLICT`. Контекст должен быть действительным, принадлежать активному creator и не быть старше attribution window.

Legacy может передавать такое же событие сервер-сервер на `POST /v1/internal/referral-analytics/events`. Этот вариант использует HMAC выше и записывает `source: legacy`; он нужен для сценариев, где браузерные cookies недоступны.

## Повторы и ограничения

Для всех Legacy → Partners запросов подпись, timestamp и nonce создаются заново на каждой HTTP-попытке. Один и тот же `eventId` и payload можно безопасно повторить после timeout или сетевой ошибки: уже принятый event вернёт `200` с `idempotent: true`. Для order events дополнительно используется dedupe key `order:{orderId}:{status}`.

Повтор с изменённым payload возвращает `409 IDEMPOTENCY_CONFLICT`. Сетевые ошибки, timeout, `502`, `503` и `429` можно повторять с backoff; `401`, `400`, `404`, `410` и `422` требуют исправления запроса или состояния. При `429` Partners возвращает `Retry-After` и `RATE_LIMITED`.

Успешное создание события возвращает `202`; повторно распознанное событие — `200`. Общий формат ошибки:

```json
{
  "status":"error",
  "error":{"code":"ERROR_CODE","message":"..."}
}
```

При отключённом модуле любой из этих маршрутов возвращает HTTP `503` с кодом `FEATURE_DISABLED` и полем `error.details.feature`.

## Order events

`POST /v1/internal/referral-analytics/order-events`

Маршрут использует HMAC-контур выше и доступен только при включённой аналитике. Пример:

```json
{
  "eventId":"4e2d7695-6025-4dbe-a8db-6a4185c6ef25",
  "eventVersion":"v1",
  "eventType":"order.created",
  "orderId":"legacy-order-123",
  "attributionContext":"v1.<payload>.<signature>",
  "status":"new",
  "amount":"249.90",
  "currency":"MDL",
  "occurredAt":"2026-11-11T12:05:00.000Z",
  "items":[
    {"legacyProductId":"11048","quantity":1,"unitPrice":"249.90","lineTotal":"249.90"}
  ]
}
```

Поддерживаются `order.created`, `order.updated`, `order.confirmed` и `order.cancelled`; статусы — `new`, `progress`, `paid`, `confirmed`, `finished`, `cancelled`. `order.created` никогда не считается подтверждённой оплатой и не создаёт запись в старом `referral_orders`. Для аналитики подтверждёнными считаются только `paid`, `confirmed` и `finished`; отмена последнего состояния исключает заказ из confirmed и показывает его в cancelled.

Для одного заказа используется dedupe key `order:{orderId}:{status}`. Повторный тот же event ID или тот же статус с тем же payload идемпотентен. Иное содержимое с тем же ID или dedupe key отклоняется. Событие со старым временем/понижением статуса либо событие после отмены отклоняется как `ORDER_EVENT_STALE`.

Для изменения состояния Legacy отправляет тот же JSON-объект, меняя только `eventType`, `status`, `eventId`, `occurredAt` и при необходимости `amount/items`. Например, подтверждение использует `"eventType":"order.confirmed"` и `"status":"confirmed"`, а отмена — `"eventType":"order.cancelled"` и `"status":"cancelled"`; `order.updated` использует один из промежуточных статусов `progress`, `paid` или `finished`.

Ответ содержит только event ID и признак идемпотентности:

```json
{"eventId":"4e2d7695-6025-4dbe-a8db-6a4185c6ef25","idempotent":false}
```

В payload и ответах нельзя передавать email, телефон, адрес, session token, пароль или платёжные реквизиты.

## Creator analytics

Оба маршрута требуют Better Auth session и `requirePartner`:

```text
GET /v1/partner/analytics
GET /v1/partner/referral-links/{id}/analytics
```

Ответ содержит `summary` и `links`. В summary есть `clicks`, `addToCart`, `createdOrders`, `confirmedOrders`, `cancelledOrders`, `revenueMdl`, `conversionRate`; `links` содержит тот же набор по ссылкам текущего creator. Доступ к чужому link ID возвращает `404`, а запрос без creator session — `401/403`.

`/v1/partner/analytics` сохраняет обратную совместимость с M4: если `REFERRAL_ANALYTICS_ENABLED=false`, запрос передаётся существующему finance-маршруту. Поэтому нельзя одновременно включать referral analytics и старый finance analytics на одном публичном пути без отдельного согласования; для текущего rollout finance и tracking остаются выключенными.

Старые `referral_link_clicks` и `referral_orders` не удаляются и не переписываются. Новые click rows связываются с attribution через `attribution_id`; при подсчёте старые rows без этой связи и новые attributions считаются раздельно, поэтому один новый click не удваивается.

## Ошибки и rollout

- `503 FEATURE_DISABLED` — контур выключен feature flag.
- `401 SERVICE_AUTH_INVALID` / `SERVICE_TIMESTAMP_INVALID` — HMAC, key ID или timestamp неверны.
- `409 AUTH_NONCE_REPLAY` — nonce уже использован.
- `400 ATTRIBUTION_INVALID` / `410 ATTRIBUTION_EXPIRED` — handoff/context недействителен.
- `409 IDEMPOTENCY_CONFLICT` — ID или dedupe key использован с другим payload.
- `409 ORDER_EVENT_STALE` — событие не может изменить уже более новое состояние.
- `429 RATE_LIMITED` — превышен database-backed rate limit; retry interval передаётся в `Retry-After`.
- `400 VALIDATION_ERROR` / `INVALID_JSON` — тело не соответствует указанной JSON-схеме.

Перед включением на dev Legacy нужно проверить отдельную базу Partners, миграцию 0018, сетевую доступность, key ring и четыре сценария: redirect/exchange, add to cart, created/confirmed order и cancellation. Production flags остаются выключенными до отдельного согласования attribution и финансов.
