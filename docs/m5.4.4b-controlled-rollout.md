# M5.4.4B — Controlled Partners production rollout

This is a runbook, not an instruction to deploy. It describes the first controlled integration test using the existing Partners production hosts and Legacy Dev.

## Scope and safety gates

- Partners hosts: `https://partners.vizaje-nica.com` and `https://partners-api.vizaje-nica.com`.
- Legacy host: `https://dev.vizaje-nica.com` only.
- No separate Partners Dev environment is deployed in this phase.
- `CREATOR_FINANCE_ENABLED=false` and `PAYOUTS_ENABLED=false` must remain unchanged.
- `REFERRAL_TRACKING_ENABLED=false` remains unchanged; the analytics handoff path is controlled separately.
- `REFERRAL_ANALYTICS_ENABLED` is enabled only for the test window, with a non-empty `REFERRAL_ANALYTICS_ALLOWED_PARTNER_IDS` containing the single approved test creator UUID.
- The analytics key ring is separate from resolver, account-linking and production key rings.

The API accepts Legacy analytics requests only after the existing HMAC middleware validates the dedicated `LEGACY_ANALYTICS_HMAC_KEYS` ring. The partner allowlist is a second server-side boundary. A partner outside the list can still use an ordinary saved referral redirect, but cannot create or exchange analytics attribution.

## Required values, kept out of Git

Configure these in the server secret manager or `/opt/vizaje/partners/.env.production` with mode `0600`; do not paste values into this document:

```env
REFERRAL_ANALYTICS_ENABLED=false
REFERRAL_ANALYTICS_ALLOWED_PARTNER_IDS=
REFERRAL_TRACKING_ENABLED=false
CREATOR_FINANCE_ENABLED=false
PAYOUTS_ENABLED=false
LEGACY_ANALYTICS_HMAC_KEYS=
```

For the test window only, set `REFERRAL_ANALYTICS_ENABLED=true`, put the exact test Partner UUID in the allowlist, and configure one active Dev key in `LEGACY_ANALYTICS_HMAC_KEYS`. The same key ID and secret must be configured in Legacy Dev. Never use `LEGACY_RESOLVER_HMAC_KEYS`, `LEGACY_TO_PARTNERS_HMAC_KEYS` or any production analytics key for this test.

## Preflight on the VPS

Run from `/opt/vizaje/partners`. These commands do not deploy or migrate anything:

```bash
cd /opt/vizaje/partners
chmod 600 .env.production
docker compose --env-file .env.production -f compose.production.yml config --quiet
docker compose --env-file .env.production -f compose.production.yml ps
docker compose --env-file .env.production -f compose.production.yml exec -T postgres \
  sh -c 'printf "db=%s user=%s\n" "$POSTGRES_DB" "$POSTGRES_USER"; pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Confirm that the printed database name is the intended Partners production database before continuing. Do not print `DATABASE_URL`, passwords or the complete environment.

## Verified PostgreSQL backup

Create and validate a custom-format backup before a migration or application update:

```bash
backup_dir=/opt/vizaje/backups/partners-production
install -d -m 700 "$backup_dir"
backup_file="$backup_dir/partners-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env.production -f compose.production.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "$backup_file"
test -s "$backup_file"
chmod 600 "$backup_file"
pg_restore --list "$backup_file" > /dev/null
shasum -a 256 "$backup_file"
```

Store the checksum with the backup. Do not delete the previous known-good backup.

## Migration 0018

Inspect the migration history without resetting or rewriting data. If 0018 is pending, apply all pending migrations once with the dedicated service; `docker compose up` does not start this service:

```bash
docker compose --env-file .env.production --profile migrations -f compose.production.yml \
  run --rm --no-deps migrate
```

This is the only migration command in the release procedure. Do not run `drizzle-kit push`, `db:generate`, `DROP DATABASE`, or a reset command. If the migration exits non-zero, keep the old API running, retain the backup, and stop the rollout.

## Application update and controlled test

Build the release images, then restart only API and Web. Do not use `down` and do not start the migration profile as part of ordinary `up`:

```bash
docker compose --env-file .env.production -f compose.production.yml build api web migrate
docker compose --env-file .env.production -f compose.production.yml up -d api web
docker compose --env-file .env.production -f compose.production.yml ps
curl --fail https://partners-api.vizaje-nica.com/health
curl --fail https://partners.vizaje-nica.com/
```

Before enabling the analytics flag, verify Legacy Dev is using the same Dev HMAC key ring and sends only to `partners-api.vizaje-nica.com`. Then update the secret configuration and restart only API:

```bash
docker compose --env-file .env.production -f compose.production.yml up -d api
docker compose --env-file .env.production -f compose.production.yml ps api
curl --fail https://partners-api.vizaje-nica.com/health
```

Use only the approved test creator and a referral link owned by that creator. Verify in the Partners database that only the expected attribution/event rows are created. Do not send real customer, order or payout data. Since finance and payout flags stay disabled, no commission or payout mutation is enabled by this test.

## Rollback

For an application or analytics problem, disable the test flag and allowlist, then restart only API:

```bash
cp .env.production .env.production.before-m54-rollback
# Edit .env.production: REFERRAL_ANALYTICS_ENABLED=false
# Edit .env.production: REFERRAL_ANALYTICS_ALLOWED_PARTNER_IDS=
docker compose --env-file .env.production -f compose.production.yml up -d api
docker compose --env-file .env.production -f compose.production.yml ps api
curl --fail https://partners-api.vizaje-nica.com/health
```

Do not automatically restore PostgreSQL. Migration 0018 is additive; an application rollback should first be tested against the retained schema. Restore the backup only under an explicit incident procedure after stopping writes and confirming the exact restore target.

## DNS and TLS

No new Partners DNS record is required for this revised plan. Confirm, before the test:

- `partners.vizaje-nica.com` resolves to the existing Partners Web host and has a valid certificate.
- `partners-api.vizaje-nica.com` resolves to the existing Partners API host and has a valid certificate.
- `dev.vizaje-nica.com` is the Legacy Dev host and is not production Legacy.

Do not create `partners-dev.vizaje-nica.com` or `partners-api-dev.vizaje-nica.com` for this phase.

## Remaining blockers before the first test

1. Confirm the exact test creator Partner UUID and put it in the allowlist.
2. Generate and exchange a separate Dev analytics HMAC key through the secret manager; do not expose it in logs or Git.
3. Confirm Legacy Dev uses the exact canonical HMAC path, raw-body hash, timestamp and fresh nonce per attempt.
4. Confirm the preflight database identity and complete backup validation on the VPS.
5. Obtain explicit approval before enabling the temporary analytics flag or applying production migration 0018.
